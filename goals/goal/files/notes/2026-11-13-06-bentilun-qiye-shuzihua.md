## 一句话

本体不是字典、不是知识图谱、不是一次性交付的文档，而是一套业务人员能读懂、程序能执行、规则引擎和大模型能共同消费的业务语义契约，是要持续迭代的知识操作系统。

## 三个常见误区（转述）

1. **本体不是数据字典**：字典只描述字段格式，本体描述概念、属性、关系、约束和公理，回答一个东西是什么、和别的东西什么关系、哪些组合是业务异常。主数据是本体里的实例，管去重清洗分发；本体是实例之上的类型和关系模型，管业务规则和分类体系，两者互补。
2. **本体不是知识图谱**：图谱是本体的一种存储和可视化载体，本体是图谱的 Schema。没有本体的图谱只是实体关系的自由罗列，容易变成脏数据集合。顺序是先做 TBox 建模，稳定后再灌入实例 ABox 形成图谱，不能颠倒。产业落地多用轻量本体即可，不必追求重型 OWL 的理论完备。
3. **本体不是一次性文档**：组织架构、业务、监管、系统一变，业务语义就变。本体必须有版本、变更流程和影响域分析，写完冻结半年后就和真实业务脱节。

## 本体五元组模型（转述）

作者的工程表达框架是类、属性、关系、约束、公理五元组，可对照 Palantir 的对象、链接、属性、时间、来源，但侧重点不同：Palantir 面向情报融合，强调溯源；作者面向企业经营、ERP、供应链、财务、合规，更强调业务约束和可执行规则。

- **类**：领域概念类型，支持继承，要满足不相交原则，互斥类不能同时成立。
- **属性**：分标识、业务、管理、审计四类，分别用于唯一识别、业务判断和管理追溯。
- **关系**：类之间的有向业务语义链接，有方向、基数和逆关系，命名必须是业务动词，这是本体区别于 ER 图外键的核心。
- **约束**：基数和取值限制，可交给规则引擎实时校验，违反就抛语义异常。
- **公理**：业务推导规则，是自动推理和 Agent 自主决策的依据。
- 同一套模型对外输出业务文档给专家评审，对内序列化到图数据库、规则引擎、向量知识库给程序消费。

## 五类语义断层（转述）

作者在 476 张业务表、497 个域类、4217 条属性的梳理中归纳出五类断层：

1. **命名断层**：同一概念在不同系统叫法不同，深层是没有统一的类定义和语义注册表，映射表只有字符串映射，不带约束。
2. **口径断层**：名字相同含义不同，如项目成本在工程、财务、物资口各指不同范围，指标字典治不了本，要靠本体把构成关系显式定义。
3. **关系断层**：两个实体有业务关系，但系统里只存了 ID，分不清是归属、配套还是关联，关系语义丢失后校验、追溯、汇总都会出错。
4. **约束断层**：强制规则散在代码、Excel、人工流程里，没有统一建模，漏掉一环就流入脏数据，故障是静默的。
5. **演化断层**：业务变了语义模型没同步更新，旧分类装不下新业务，只能乱填，脏数据越积越多。

## 两类静默错误（转述）

作者复盘的一次事故统计偏差达 15.6%，根源是缺少互斥约束和基数约束：验收单的待验收和已验收是两个独立布尔字段，可同时勾选，报表两边重复计数。数据格式合法、接口返回成功，但业务逻辑已经错了。事后清洗只能清存量，治本是把约束和公理写入本体，由语义网关或规则引擎前置校验。但本体不是万能防火墙，不能替代业务审批和人工判断。

## 本体建设十步法（转述，步骤名）

划定领域边界拆本体域 → 业务专家访谈收集术语 → 识别核心类建立层级 → 定义属性区分标识与业务属性 → 识别关系定义方向基数逆关系 → 编写约束与公理 → 和现有数据系统做映射对齐 → 小批量实例灌入做一致性校验 → 接入规则引擎、指标平台、知识库、Agent → 建立变更治理流程持续迭代。最容易被压缩的是第一步和第十步，跳过边界划分又没有长期治理，本体最后会腐化失效。

## 三个出口与 Agent

- 三个出口同源：一是给业务人员的可读文档，二是给引擎的可执行规则，三是给知识库和图谱的实例层。
- Agent 不应靠长 Prompt 塞业务规则，而应基于本体定义动作空间：本体提供概念字典、关系字典、约束和公理，模型负责理解自然语言并映射成本体上的合法动作，本体负责校验和拦截非法动作。规则收敛在本体一处，变更只改本体，所有 Agent 自动继承，行为也可审计。
- Palantir 不能直接照搬的三点：场景目标不同（情报重溯源，企业重强合规强内控刚性约束）、组织权责不同（分析师主导 vs 多部门交叉评审）、数据治理基线不同（外部非结构化为主 vs ERP 等结构化系统为主，首要矛盾是系统间语义冲突）。

## 组织保障与边界（转述）

- 三类角色缺一不可：业务域 Owner（概念定义决策权）、本体工程师（建模映射版本管理）、IT 平台负责人（存储、规则引擎、图谱、消费端）。权责倒置（IT 定义业务概念、业务只签字）是常见死因。单域落地约十二周。
- 本体不能做的五件事：替代业务审批流、替代数据清洗、替代主数据/数仓/指标平台、降低业务共识成本、消除非结构化文本的全部歧义。

## 与 Nakamura 现有工作的关联

- **与第 4 篇 Semantica 直接互补**：第 4 篇讲分层和模块，这篇讲每一层里语义该怎么建、怎么治理。拿五元组和十步法对照自家 Galaxybase、GI、G-KG、知寰、知域灵枢一整条线，能定位缺的是建模方法还是治理机制。
- **园区本体图谱的验收标准**：每条边都要有业务动词命名、方向、基数和约束；约束缺失的故障是静默的，报表数字看着正常，业务已经错了——节约核验图谱尤其要防这一点。
- **Agent 落地路线**：不要把业务规则写进 Prompt，规则收敛到本体，Agent 的动作空间由本体定义，这正是知域灵枢多智能体要走的路。
- **给客户讲本体的方法**：先讲三个误区和五类断层（客户的痛），再讲五元组和十步法（怎么做），最后讲边界（不承诺什么），这个顺序比直接讲 OWL、RDF 更容易让业务方点头。
