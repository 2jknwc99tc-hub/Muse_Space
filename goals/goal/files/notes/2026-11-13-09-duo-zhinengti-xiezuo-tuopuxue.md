# 多智能体协作的拓扑学：Swarm、Hierarchical、Ring——哪种架构适合你的场景？

## 一句话

多一个 Agent 不一定多一份能力，还可能多一条等待链；决定多智能体系统表现的不是模型多聪明，而是协作协议有没有写清楚：谁能找谁、谁有权派活、谁必须回复、什么时候停止。

## 关键点（转述，非原文照抄）

1. **先分开三层概念**：协作拓扑回答谁与谁协作、谁掌握控制权；通信模式回答一条消息怎样送达、如何关联回复；框架实现回答用什么抽象组织运行过程。实际设计要画两张图，通信图说谁能给谁发消息，控制图说谁能决定下一步，两者可以不同。Swarm 是一种分散协作的设计范式，不意味着必须全连接；OpenAI Swarm 是一个具体项目，以轻量交接演示编排，不能直接等同于并行蜂群。
2. **三种拓扑各有适用场景**：Swarm 是动态路由，让最合适的专家接手下一步，没有每一步都必须经过的中心领导，适合任务边界不清、下一步取决于新证据的开放式故障定位、探索性研究、跨领域分诊，代价是路径难预测，全员自由对话很容易变成一场昂贵的群聊，工程上要限制候选协作对象、给交接附上转交原因和已完成与还缺什么、给总交接次数和重复路径设上限，判断循环要看状态有没有进展，不能只看节点有没有重复；Hierarchical 是层级统筹，管理者拆解目标、分配给执行者、最后统一验收，适合任务可以分解、交付标准明确、需要统一口径的企业研究报告、批量数据处理、带验收规则的代码修改，优势是责任清楚、容易定位失败分支，代价是管理者可能成为延迟瓶颈、也可能把错误拆解传播给整个团队，管理者应该发任务合同而不是一句帮我研究一下，合同要写清输入的数据范围、截止日期和允许使用的资料，输出的固定结构、证据定位和无法完成时的错误状态，验收的必填字段、计算规则和哪些缺项必须阻断最终结论，步骤完全固定时管理者甚至不必是语言模型，确定性工作流可以负责调度；Ring 是有界接力，按起草者、评审者、修订者、起草者的固定次序传递，重复若干轮、达到验收条件后退出，适合角色顺序稳定、每一步会修改上一版产物的方案论证、文稿审校、测试驱动修复，底线是有界，限定轮数、明确通过标准、指定最终裁决者，没有新证据、没有新增有效修改时应停止迭代，环形不一定省上下文，只有把传递物限制为当前产物、变更摘要和待解决问题时才可能控制上下文增长，轮流发言也不等于点对点环形通信。
3. **三种通信模式各管什么**：广播适合共享目标变更、关键约束、最终停止信号，价值是同步共同事实，不是让每个 Agent 对每条消息都再做一次推理，全员接收可以，按需激活更重要；发布订阅按主题分发，生产者不必认识消费者，增加消费者不必让生产者改接收人名单，但发布订阅本身不承诺持久化、顺序性或恰好一次处理，这些要看消息中间件、运行时配置和消费逻辑，链路可能重复投递时消费者要按消息标识去重，必须保序时要按任务键分区或增加版本检查；请求回复给一项明确有边界的能力调用一个可追踪的答案，消息信封要包含消息标识、运行标识、任务标识、任务版本、关联标识、尝试次数、截止时间、幂等键和载荷引用，关联标识把回复关联到请求，任务版本隔离旧输入，尝试次数区分重试轮次，幂等键防止同一业务操作重复生效，大文件通过引用传递并校验版本或内容哈希，不要把聊天记录当数据库。
4. **框架对照先问谁拥有最终答案**：OpenAI Swarm 与 Agents SDK 的代表机制是交接转移当前控制权，容易踩的坑是把交接当成自动并行，官方区分交接让专家接管后续对话与把 Agent 当工具让管理者继续负责最终回答两种模式；AutoGen AgentChat 的代表机制是角色对话与团队发言调度，要先确定谁发言、谁能看到消息，容易踩的坑是把聊天轮数当成任务进度；CrewAI 层级流程的代表机制是管理者分配任务并检查结果，要先确定谁拆解、谁验收，容易踩的坑是认为管理者天然保证正确性。选框架前先回答谁拥有最终答案，比问哪个框架能放更多 Agent 更接近架构核心。
5. **让系统真正跑完要处理死锁、超时、聚合**：死锁是互相等待且没有外部事件能让它们继续前进，活锁是双方一直转交、一直修改但状态没有实质推进，慢工具和长推理又是另一类问题，维护一张等待图，在简化模型中环是死锁的重要判据，对任一结果到达即可继续的依赖或带外部事件的等待，发现环不足以宣布死锁，可以用强连通分量找出候选等待环，再检查超时、替代路径和可运行任务，发现异常后按策略取消某条等待、降级为缺项结果或交给上级裁决，活锁的信号是产物哈希不变、已验证证据数不增、同一问题重复转交，监督器应在 Agent 循环之外；超时至少需要工具调用超时、子任务超时、整次运行截止时间三层限制，重试和交接都应消耗同一份总预算，每次调用前按工具上限、子任务剩余时间和全局剩余时间减去收尾预留三者取最小值，超时小于等于零时不再启动新调用，只对可恢复错误重试，参数错误先修正，业务拒绝不应原样重试，采用有上限的指数退避并加入抖动，等待时间同样计入预算，超时不代表远端操作已经停止，取消应传递到工具层，有副作用的操作重试前应通过幂等键或状态查询确认是否已生效，迟到结果必须通过当前任务版本、有效尝试编号和任务状态检查才能被接纳；聚合要先验证证据再组织语言，让最后一个 Agent 总结一下只完成了表达层，没完成正确性检查，统一子任务结果结构，证据引用应能定位到文档、版本、页码或原始记录，聚合分校验结构与身份、按业务键合并、处理冲突、决定交付状态四步，多个 Agent 可能共享同一错误来源，多数票不能自动证明事实，模型自报的置信度也不能直接当成经过校准的概率，必需任务全部通过才标记完成，可选任务超时可给部分结果并明确缺项。
6. **同一个项目可以组合三种拓扑**：以企业研究简报助手为例，第一层用层级做主干，规划节点拆成业务资料、财务指标、风险证据三个任务，每项都有输出结构和独立截止时间，财务计算用确定性工具完成，Agent 负责定位数据和解释口径；第二层用 Swarm 思路处理局部探索，研究分支遇到需要行业知识的问题可以转交专家，但只允许预先登记的协作边，每次交接记录理由并扣减跳转预算；第三层用 Ring 做有限复核，初稿到核查再到修订最多两轮，核查清单固定为数字、时间、引用和推断边界，两轮后仍有无法解决的证据冲突就保留分歧或按事先定义的规则转人工处理。风险分支在截止前没有完成时，如果是可选项可以交付部分完成的简报并说明风险分析缺失，如果用户明确要求完整风险核验就应停止完整交付，返回可读的失败原因及已完成材料，降级是否允许必须由任务合同决定。并发调度要写进运行时，控制面是显式的，模型只在需要判断的地方参与。
7. **选型速查是先看任务再看框架**：下一步取决于新发现、路径不固定时优先尝试受限 Swarm 或交接网络，必须补上路由白名单、跳转预算、进展检测；可以拆任务、需要统一验收与口径时优先尝试层级，必须补上任务合同、依赖管理、管理节点恢复；角色顺序稳定、产物需要反复修订时优先尝试有界 Ring，必须补上轮数上限、产物版本、退出标准；大量独立任务、追求吞吐量时优先尝试工作队列加并发执行者，必须补上限流、背压、幂等、失败队列；步骤固定、几乎不需要动态决策时优先尝试确定性工作流，必须补上状态持久化、可恢复执行；一个 Agent 加工具已经能稳定完成时保持单 Agent，必须补上评测与工具质量。只有当分工带来的质量、延迟或维护收益覆盖通信与调度成本时，增加 Agent 才有意义。第一次选型实验要保留单 Agent 基线，用同一批任务比较候选架构，先固定模型、工具与任务范围，记录质量、延迟、成本、稳定性四类指标，再注入工具变慢、同一消息重复到达、某个分支返回相互矛盾证据三类故障，能在这些条件下按规则结束，才说明系统有了工程上的闭环。
