## 一句话

Neo4j 在 2026 年 11 月 5 日发布并开源了 Ontology Graph Specification，一种用 JSON 或 YAML 描述领域知识的机器可读格式：Schema 只告诉 Agent 图里有什么，本体才告诉 Agent 那些东西是什么意思。

## 关键点（转述，非原文照抄）

1. **两天之内，第二份本体声明**：11 月 3 日 Snowflake 在 Expedition 2026 上发布 Business Ontology，让 Agent 基于已审批的业务定义作答；仅隔两天，11 月 5 日 Neo4j 发布并开源 Ontology Graph Specification。两家切入角度不同：Snowflake 从目录与治理切入，本体是 Horizon Catalog 里的受治理上下文层；Neo4j 从图数据本身切入，本体是图模型之上的领域语义层。但诊断的是同一个病灶：一个查询图数据的 Agent 需要知道 Account 可能指银行账户也可能指支付账户，知道人们口语里管它叫 bank account，知道 IBAN 是它的标识号，这些知识过去散落在文档和数据字典里。同期背景还有 Palantir Foundry、Databricks Genie、Microsoft Fabric IQ 各自的本体化实践，以及 Snowflake 联合创立的开放语义标准 Apache Ossie。
2. **三大设计原则**：务实，规范提供清晰、可读、机器可处理的实体、关系、属性与业务含义描述，刻意设计成融入团队现有的开发、集成与运维工作流，而不是要求先学一整套形式逻辑；可互操作，W3C 的 RDFS、OWL、SKOS、SHACL 仍是重要基石，但今天组织使用本体的方式已经大大扩展，规范文档明确说明了 RDFS 与 SHACL 概念的映射方式，目前没有定义 RDF 序列化格式，未来可能补充，这是一次有意的取舍，先服务当下的图与 AI 应用，再谈与经典语义网栈的对齐；AI 优先，这不是把老标准换个包装，而是为 Agent 时代的新架构原生设计，描述、别名等字段的存在理由只有一个，让 Agent 工作在领域含义之上，而不只是 Schema 里碰到的标签。
3. **核心原语共六组**：节点与关系，以稳定标识为键，可带标识性标签、隐含标签、可选标签、描述与别名，隐含标签实现了层级语义，例如声明 Customer 蕴含 Person；属性，支持完整的 Neo4j 类型系统，包括时间、空间和向量类型，后者显然是为向量检索场景准备的；基数，关系两端可声明最小与最大数量约束，例如每人至少拥有一个账户；约束，存在性、唯一性、键、属性类型四类，并提供简写形式，展开后即为完整的约束对象；reference 字段，每个元素都可回链到外部定义，即公开标准本体术语或文档，这是与传统语义网世界保持血缘的关键；命名扩展，索引、显示提示、数据源映射等工具关注点放进扩展区，与模型本身分离，领域知识不被工具细节污染。
4. **一份本体就是一个文档**：用 JSON 或 YAML 写，对照一份公开发布的 JSON Schema 做校验。版本化的 Schema 不可变，current 别名始终指向最新版。规范采用语义化版本：破坏性变更必须升主版本，新增能力以向后兼容的次版本发布。博客给出的反欺诈领域最小示例很能说明设计意图：Person 的别名是 customer、account holder，邮箱唯一；Account 的别名是 bank account，IBAN 作为键；Person 到 Account 的 OWNS 关系写的是法律上的所有权，要求每个 Person 至少关联一个 Account。别名是给 AI 准备的，描述写的是业务含义而不是技术注释，约束简写和基数约束都直接落在业务规则上。
5. **一份本体，多种用途**：同一份本体文件可以同时服务多个场景，数据库层作为数据约束集强制执行，数据工程编写本体驱动的逻辑用于数据推导或富化，应用与 Agent 把它作为解释和操作信息的上下文。写一次本体、处处使用，团队只需维护一份规范文件，数据库、导入工具、文档智能、Agent 和自建工具读的都是同一个工件。这份工件是发布过的、版本化的、有 SDK 支撑、开放治理的，Neo4j 称之为一个可以放心构建的稳定契约。配套 SDK 覆盖 JVM、JavaScript 与 TypeScript、Go 三种语言，采用 Apache 2.0 协议开源，仓库在 GitHub。
6. **对六类角色意味着什么**：应用开发者，一份 YAML 或 JSON 文件，经公开 JSON Schema 校验，可用 SDK 读取，节点、关系、约束、索引一处定义；数据工程师，同一份文件承载约束、索引与数据源映射，内置校验器确认 Schema 可在 Neo4j 中创建、映射可用于数据导入；知识工程师，捕获概念的定义、同义词、层级及与标准术语的链接，人和工具读同一个版本化文件，无需维护独立的术语表；W3C 拥抱用户，没有 RDF 序列化，但文档说明了 RDFS 与 SHACL 概念的映射方式，reference 字段把每个元素链回已在用的标准术语；Agent 构建者，描述与别名告诉 Agent Account 是什么、人们还怎么叫它，Agent 基于领域含义工作，而不只是 Schema 标签；数据团队负责人，领域只定义一次，作为版本化的开源文件，人、工具、Agent 共读，需要评审和保持最新的定义只有一份。
7. **上手路径与行业观察**：官方建议的入门三步是为已在运行的图写一份模型，手工或借助 Agent 生成；用任意校验器检查它；告诉官方你表达不了什么，通过开源 issue、跟进 release 或直接贡献代码。文章的判断是：企业 AI 的下一层竞争不在模型，在语义地基。本体正在成为数据平台的新战场，Neo4j 这份规范的特殊价值在于选择了开源加开放治理的路线，本体不是某一家的私有资产，而是可以流动的领域契约，这和 Snowflake 支持 Ossie 与 RDF 导出的姿态形成呼应，本体的价值恰恰在于共享，封闭的本体只是一张更大的数据字典。当然也要看到取舍：暂无 RDF 序列化、生态伙伴尚在起步、与 W3C 全家桶的对齐依赖映射文档而非原生兼容，对重 RDF 资产的组织，迁移仍有摩擦。但作为一份务实优先的开源规范，它给让 Agent 理解业务含义这件事提供了目前最轻量的起步方案：一个 YAML 文件，一次定义，处处生效。
