# Agent 都能自己查数据了，还要花钱建本体、知识图谱吗？

- 记录日期：2026-11-24（北京时间）
- 标题：Agent 都能自己查数据了，还要花钱建本体、知识图谱吗？
- 来源：微信公众号 叶小钗，作者 叶小钗（标注“原创”），发布于 2026-11-23 09:00
- 原文链接：https://mp.weixin.qq.com/s/ZUMotpdk0H1VAgGcjf-MgQ
- 主题标签：本体论、知识图谱、业务建模、Agent、业务语义层、ROI

## 一句话

复杂 AI 应用真正绕不开的是业务建模，本体不是所有 AI 项目的必选项，它只为其中需要被独立理解、查询和复用的业务语义提供一种形式化表达；语义层一旦独立，Agent 获得的就不是更多数据，而是正确使用数据的能力。

## 关键点（转述，非原文照抄）

1. **认知断层与核心问题**：现在做 AI 项目存在一个很有意思的认知断层，大家已经意识到，复杂 AI 应用最终需要一套业务模型来支撑，但还没有真正理解 Ontology 究竟解决了什么问题，以及它在整个 AI 系统中承担什么职责。这也是为什么很多人知道本体很重要，研究了本体论、知识图谱、业务语义、实体关系，却很难回答一个实际问题：我把 Ontology 建出来以后，到底能用它干啥？之前作者一遍一遍的说，AI 项目的核心是 SOP + 数据，一个 AI 项目可以按照 SOP 复杂度和数据复杂度分成 12 类，遇到的各种智能体项目，基本都可以在这个框架里找到对应的位置。那么，为什么复杂 AI 项目做到深处，经常会碰到本体和图谱？如果去问或者搜这个问题，通常会得到这样一个回答：AI 不只是需要数据，还需要理解数据背后的业务含义，以及数据之间的关系。这个回答没问题，但问题是，知道了这个结论以后，是不是依然不知道能用他来干啥？
2. **本质是业务复杂度**：做 AI 应用，本质上是在处理业务复杂度，我们做企业 AI 应用，本质上是要将一部分真实业务交给机器处理，业务越复杂，我们需要对业务进行的理解、抽象和工程实现也就越复杂。这里可以建立一个简单的理解框架：业务复杂度 ≈ 工程复杂度 + 数据复杂度。当然，这不是一个严格的数学等式，而是一种拆解业务复杂度的思路。在将真实业务转化为 AI 应用的过程中，我们可以通过两套模型承载业务复杂度。业务运行模型：解决工程复杂度，业务运行模型主要解决业务如何运行的问题，我们可以通过 SOP、业务规则、算法、Workflow、Agent 等方式的组合，实现业务的判断、决策和执行，例如 SOP 描述业务执行过程，业务规则描述业务判断逻辑，算法负责计算、预测和优化，Workflow 组织相对确定的执行路径，Agent 处理动态理解、规划和不确定性任务。业务表达模型：解决数据复杂度，业务表达模型主要解决业务信息如何被机器表达和使用的问题，这里实际上包含两部分：第一部分是如何构造数据，我们可以根据业务建模的结论，建立服务于数据组织和处理的数据模型，也可以通过 Ontology 等方式，建立服务于业务语义定义的模型；第二部分是如何使用数据，这就涉及数据工程，包括数据采集、存储、查询、关联、检索、上下文构建等工作，也涉及关系型数据库、图数据库、向量数据库等技术选型。最终，通过接口、Tools、数据服务等方式，让业务运行模型能够调用业务表达模型，共同构成一套可运行的 AI 业务系统。业务建模：决定如何高效地表达业务，那么，这两套模型是怎么来的？这就涉及业务建模，业务建模的核心任务，是通过对真实业务进行分析和抽象，找到一种能够高效表达业务逻辑的方式，业务建模形成的抽象结论，一部分通过 SOP、规则和算法等方式进入业务运行模型，一部分通过数据模型、语义模型等方式进入业务表达模型。所以，面对同一个业务问题，不同的人可能会设计出完全不同的系统，有人通过大量 Workflow 分支解决问题，有人通过规则引擎解决问题，有人通过重新设计数据模型解决问题，还有人将大量业务信息交给 Agent 动态处理。这里需要考虑的是：我们应该如何分配和承载业务复杂度，才能获得更高的工程 ROI？
3. **大力出奇迹，还是按需建模**：围绕这个问题，我们通常可以看到两种不同的思路。第一种：大力出奇迹，原理很简单，既然 AI 需要理解业务世界，那我们就尽可能完整地对业务世界进行结构化描述，让机器知道：业务世界里有什么对象和概念，这些对象分别具有什么属性和状态，对象之间存在什么关系，这些概念、状态和关系有什么业务含义，业务中存在哪些知识和约束。在此基础上，通过 Ontology 等建模方式构建业务语义层，再通过数据工程提供查询和访问能力，让 Agent 能够自主获取和使用这些业务信息。为什么叫它大力出奇迹？这条路线背后有一个很性感的假设：现在模型能力和 Harness 能力已经这么强了，未来还会继续增强，只要提供足够丰富的业务上下文，并且给这些上下文构建足够完善的语义模型，Agent 就可以自己查数据、构建业务上下文、分析问题并调用（原文此处语句未完整显示），这样，就不用去做无聊的 Workflow 穷举和各种基于 workflow 的工程化了，这似乎是一种解决企业有大量业务系统和复杂业务关系的情况下如何落地 AI 的捷径？但它的问题是，我们需要投入大量成本对业务世界进行建模，却不一定知道这些模型最终会被哪些业务场景使用，以及能产生多少业务价值。对，他没有回答我们前面的问题：我把 Ontology 建出来以后，到底能用它干啥？这有点像即时战略游戏里的一种玩法：只要我把科技树全部点满，我就是无敌的，这没错，但没什么实际指导意义，因为真实项目里的资源永远是有限的。第二种：拆解复杂度，按需建模，另一种思路就比较传统了，我们从具体业务场景出发，先梳理业务 SOP，根据 SOP 中每个环节所需要的信息设计对应的数据结构，再通过程序、规则、算法和 Workflow 实现业务逻辑。如果业务比较简单，这套方式完全没有问题。随着业务复杂度增加，我们可能会发现，继续增加 SOP 分支和判断规则，工程实现成本越来越高。这时候，我们可以通过重新进行业务建模，找到一种更高效的业务表达方式，调整对应的业务逻辑和数据结构，将一部分原本固化在程序中的业务逻辑转化为由数据模型承载。这就是我们前面说的，通过业务建模，重新分配工程复杂度和数据复杂度，从而获得更高的工程 ROI。但到这里，本质上仍然是传统的软件开发逻辑。当业务进一步复杂，部分业务判断和执行路径难以提前确定时，我们可以引入 Agent，承担部分动态推理和决策工作。这时候就会出现一个新的问题：原本由开发人员理解、并且固化在程序中的业务语义，应该如何被 Agent 理解和使用？如果通过简单的数据说明和工具接口已经无法满足需求，我们就需要考虑将这些业务语义独立表达出来，构建业务语义层，Ontology 就是构建这套语义层的一种方式。
4. **案例拆解：销转 Agent**：假设我们要做一个在线教育的销售转化 AI 应用，帮助销售人员将购买了低价体验课的用户转化为正价课用户。首先，我们需要梳理销售 SOP，一个简化的流程可能包括：获取客户信息，进行初步沟通，了解客户需求，跟进客户的体验课学习情况，介绍正价课产品，与客户沟通，推进购买决策，记录销售结果。在此基础上，我们可以按照每个 SOP 节点的需要，设计相应的数据结构，例如客户信息表、课程信息表、沟通记录表、销售阶段表、话术库、订单信息表等。比如，我们可以收集销冠在不同销售阶段的历史沟通记录，提取其中的优秀问答，形成各个销售阶段的话术库。当客户发来一条消息时，系统按照以下逻辑执行：判断客户当前处于哪个销售阶段，获取当前阶段的应答 SOP，检索该阶段的话术库，匹配类似问题的销冠回答，结合当前客户信息和沟通上下文，将检索到的内容组合成一条应答消息。然后通过规则、程序或者 Workflow（低代码框架）实现具体的业务逻辑。如果业务比较简单，这套方式完全没有问题，但随着业务深入，情况可能会发生变化。假设企业有多个品类的课程，例如超级 AI 个体课、FDE 主体课、Agent 主体课，每个品类又有初级、中级和高级等不同课阶，不同课阶的销售过程中，又有破冰、课程跟进、销售、逼单等不同阶段，同一个用户（原文此处语句未完整显示），那么，我们原来的话术匹配逻辑就可能变成：产品品类 × 课程等级 × 销售阶段 × 用户问题 → 推荐话术，随着业务变量越来越多，需要处理的组合也越来越多，新增一个品类、调整一个销售阶段，可能就需要重新整理大量业务规则和话术。这时候，我们通常会继续穷举 SOP，补充业务规则和话术，同时提取共性逻辑，通过公共规则、函数或者子 Workflow 减少重复开发，但这样依然是在原有业务建模的基础上进行工程优化。可能大家会想，能不能将大量业务信息交给 Agent，由 Agent 根据当前情况动态判断应该如何应答，但这样又回到了大力出奇迹的思路了，而且这样的效果大概率是不好的，大家可以试试。大家可以思考一个问题：我们能不能换一种方式表达这个业务，从源头上减少需要处理的业务组合？这就需要我们重新研究业务，找到一种更高效的业务表达方式。
5. **实践解法 + 最佳实践**：作者说之前在这块是有最佳实践的，只不过不能完整的告诉大家，大家可以参考这张图，这里可以简单提示两句：按品类×课阶×销售阶段×客户异议匹配话术，每新增一类课程，都可能多出一整套规则，但如果把转化障碍作为核心实体，就能把销转逻辑拆成诊断与决策两层。比如客户说“太贵了”，诊断模型要根据客户行为和沟通记录，判断他是预算有限，还是担心学不会，决策模型再结合课程特点和销售阶段选择策略，前者可以调整课程方案，后者可以安排一次试听，话术到这一步才生成。经过真实业务验证，共性的判断逻辑就能跨品类复用，新增课程时，只需补齐课程知识、案例和差异化规则。至于更多的内容，这里就没办法提及，感兴趣的同学可以看看我们的 AI 体系训练营，这里省略约 5000 字。
6. **引入 Agent 做推理层**：随着业务进一步复杂，我们可能会发现，即使已经建立了诊断模型和决策模型，也仍然存在大量难以提前确定执行路径的情况。例如，一个客户在沟通中同时表达了以下信息：「课程还是有点贵，而且之前体验课我就有点跟不上，最近时间也比较紧，我再考虑一下吧。」这里可能同时涉及价值认知、效果信任、时间安排和购买意愿等多个问题。如果完全通过 Workflow 处理，我们需要提前确定：针对这个客户需要查询哪些信息，应该优先诊断哪个转化障碍，信息不足时应该进一步了解什么，多个转化障碍应该按照什么顺序处理，当前应该采用什么策略。这些判断具有较大的不确定性，我们就会考虑引入 Agent，让它承担部分动态推理、决策和执行工作。但这时候出现了一个新的问题。原来的业务语义在哪里？在基于 Workflow 的 AI 应用中，我们其实已经在使用业务语义了，假设我们在 Workflow 中设计了一个 LLM 诊断节点，为了让 LLM 完成诊断，我们需要提前确定：什么是转化障碍，有哪些转化障碍类型，不同转化障碍的诊断标准是什么，当前需要获取哪些客户信息和沟通记录，购买异议与转化障碍之间是什么关系，最终需要输出什么样的诊断结果。然后，通过代码、数据查询和上下文工程，将这些业务语义、判断标准和实际业务数据组织起来，提供给 LLM，由 LLM 完成具体的业务判断。也就是说，LLM 已经具备业务推理能力，但是它需要什么业务语义、获取什么数据、完成什么推理任务，主要是由开发人员在设计 Workflow 时提前确定的，业务语义已经存在，只不过它被分散地封装在不同 Workflow 的代码、Prompt 和上下文构建逻辑中。但当我们引入 Agent，希望它能够根据实际业务情况，自主判断应该查询什么数据、如何构建业务上下文、完成什么推理任务、调用什么业务能力时，情况就发生了变化，原来由开发人员在系统构造阶段提前完成的工作，现在有一部分需要交给 Agent 在业务运行阶段动态完成，这就要求 Agent 知道这些数据的业务含义、关联关系，以及在什么情况下应该如何使用。如何让 Agent 理解业务语义？最简单的方式，是通过 Prompt、字段说明、业务文档和 Tools 的接口描述，告诉 Agent 这些业务概念是什么意思，以及应该如何使用。例如，我们可以给 Agent 提供几个业务工具：查询客户的当前销售机会，查询客户的学习情况，查询历史沟通和诊断记录，查询某种转化障碍对应的候选策略。同时，在 Prompt 中说明这些工具分别在什么情况下使用。如果业务比较简单，这种方式完全足够。但如果业务概念越来越多、数据关系越来越复杂、Agent 需要处理的任务越来越多，我们可能会发现，每个 Agent 都需要大量描述业务概念和关系的上下文，同时，我们还需要不断设计新的工具接口和数据关联逻辑。这时候，我们就需要考虑：能不能将这些原本分散在业务文档、Prompt 和程序中的业务语义独立出来，形成一套机器可以查询、理解和使用的业务语义模型？这就是构建语义层的思路，而 Ontology，就是构建语义层的一种方式。当然，这不是说我们必须先把 Agent 做出来，再建设语义层，业务语义层本身也是企业基础设施之一，本体建模在 AI 出来之前就被广泛研究了，但主要作用是用于显性化描述领域知识，让业务世界能够理解和讨论（原文此处语句未完整显示）。

- **与第十九篇六力架构、第二十三篇 project44 呼应**：第十九篇说可信靠可观测、可控靠可干预、可解释靠可追溯；第二十三篇说先立业务定义再谈模型，答案必须能追溯到数据；这篇说本体是业务语义的独立表达，语义层一旦独立，Agent 获得的就不是更多数据，而是正确使用数据的能力。三篇合起来，先懂业务定义，再查数据，模型只做解释，语义层是让 Agent 正确使用数据的前提。
- **与第一篇 FDE 呼应**：第一篇说 FDE 的本质是产品化咨询，“问题在 3 个以上客户处独立出现就是产品信号”，定制代码占比要逐年下降；这篇说销转逻辑拆成诊断与决策两层，经过真实业务验证，共性的判断逻辑就能跨品类复用，新增课程时只需补齐课程知识、案例和差异化规则。两篇合起来，共性判断逻辑跨场景复用，就是产品化的起点。
- **与第十三篇流程呼应**：第十三篇说流程要把经过验证的业务方法沉淀下来，让个人经验成为组织能力；这篇说业务建模寻找高效表达业务的方式，本体只是为其中需要被独立理解、查询和复用的业务语义提供一种形式化表达。两篇合起来，沉淀的不是术语表，而是被人工裁定过的规则和业务语义。
